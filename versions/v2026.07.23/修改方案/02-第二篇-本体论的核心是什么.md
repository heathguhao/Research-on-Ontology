# 第二篇《本体论的核心是什么》修改方案

## ISSUE I2-01：把“谓词是核心”限定为工程组织命题（不采纳）

- **优先级**：P1
- **类型**：逻辑边界
- **评审状态**：不采纳，关闭，未执行。
- **原建议**：把“谓词是本体论核心”收窄为只对某些工程系统成立的组织命题，以免压低对象、事件、过程、制度和测量体系的地位。
- **不采纳理由**：压低这些要素作为本体论中心的地位，正是第二篇的目的。面向对象的思路习惯先把对象当作世界的中心，再把关系和行为附着到对象上；本篇要反过来主张，对象只有进入关系、性质、约束和行动之后，才获得可理解、可判断和可操作的意义。对象、事件、过程、制度和测量并未被删除，但都要进入谓词所组织的结构中，不再各自占据中心位置。
- **立场说明**：“谓词是核心”是本系列主动提出的理论主张，不需要伪装成从既有逻辑或范畴论中自动推出的唯一结论。它的独创性就在于明确改变中心：从“有什么对象”转向“对象之间成立什么、应当怎样、能够做什么”。为了打破面向对象思维已经形成的默认地位，论述不退回温和的并列主义，也不为每次出现的“谓词是核心”附加工程任务限定。
- **关闭边界**：保留“谓词是本体论核心”的强命题。引用逻辑学或范畴论可以帮助说明关系视角，但不把任何既有定理冒充为这一原创立场的形式证明。

## ISSUE I2-02：给 Link、Property、Action 建立共同边界

- **优先级**：P1
- **类型**：逻辑边界
- **评审状态**：评审通过，未执行；实施须另行取得明确授权。
- **问题**：Link、Property 和 Action 都被纳入 `ontology.proto`，也都服务于谓词中心的总体结构，但三者承担的具体功能并不相同。如果只强调共同性，读者可能看不清关系、取值和行动之间的差别；如果只强调差别，又会看不见它们为什么能够进入同一套本体框架。
- **修改动作**：先建立共同边界：三者都是在 Proto 中被明确声明、命名、约束、版本化和治理的谓词结构。再分别说明：Link 表达对象之间成立什么关系，Property 表达对象具有何种可约束的性质，Action 表达在什么条件下可以做什么以及做完后发生什么变化。三者共同归入谓词体系，但不抹掉各自的语义和执行差异。
- **建议落点**：第 4 节统一表、第 5 至 7 节定义、命题 8.4。
- **验收标准**：读者能够从一张表看出三者在 Proto 中的共同位置、共同治理方式和不同作用；共同边界能够支持“谓词是核心”，差异说明又不会把三者写成彼此的简单变体。

## ISSUE I2-03：区分本体、符号控制面与执行治理（不采纳）

- **优先级**：P1
- **类型**：工程边界
- **评审状态**：不采纳，关闭，未执行。
- **原建议**：把本体、符号控制面和执行治理严格分成三层，限制谓词系统的覆盖范围。
- **不采纳理由**：这种分层方式虽然符合常见的企业架构习惯，却会把本体重新缩回概念字典，把约束、决策和行动交还给彼此割裂的系统，正好取消了本篇想要提出的新东西。谓词不只描述“世界中有什么关系”，还要连接“什么条件成立”“什么行动可以发生”“行动之后什么发生改变”。符号控制面之所以成立，就是因为定义、判断和行动能够沿着同一套谓词语义贯通。
- **辩护方式**：正文不必把这种立场写成一个无所不能的超级平台。数据库、规则引擎、权限系统、工作流和现场设备仍可以承担各自的实际执行；但它们使用的概念、条件、约束和行动接口，应当由谓词中心的本体结构统一说明和连接。工程实现可以分布，语义中心不能再次分裂。
- **关闭边界**：不增加把本体、符号控制面和执行治理彼此隔断的三层边界。可以说明不同系统如何分工、授权和保证安全，但这些说明必须服务于谓词中心，而不能把谓词降为执行系统之外的一份被动说明书。

## ISSUE I2-04：增加与既有企业系统共存和停止建模条件

- **优先级**：P2
- **类型**：工程边界
- **评审状态**：评审通过，未执行；实施须另行取得明确授权。
- **问题**：传统信息化读者会追问，本体与主数据、数据标准、接口规范、规则引擎、BPM 和 API 管理相比增加了什么，以及何时不值得建设本体。
- **修改动作**：增加“何时需要本体，何时不需要”小节。只有当同一套含义需要跨系统复用、长期维护、处理冲突或约束行动时，才进入本体；局部字段校验、单系统流程和短期接口映射继续留在原系统。说明何时停止继续建模，以及已有本体何时可以降级或退出。
- **建议落点**：结论前新增工程决策表。
- **验收标准**：给出适合建设本体和只需使用现有技术的典型场景；明确“并非什么都要本体化”，并避免同一内容在本体与原系统中无人负责地重复维护。
