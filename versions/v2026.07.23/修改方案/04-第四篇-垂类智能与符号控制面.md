# 第四篇《垂类智能不是一个模型》修改方案

## ISSUE I4-01：说明符号控制面相对既有技术组合的增量

- **优先级**：P1
- **类型**：工程边界
- **评审状态**：限定范围通过，未执行；实施须另行取得明确授权。
- **问题**：读者可能会问，已有的数据库约束、规则引擎和工作流也能实施控制，符号控制面为什么仍有必要。这个问题可以回应，但不是第四篇的主旨，不值得展开成既有技术盘点或架构选型讨论。
- **修改动作**：只作简短交代：既有工具通常各自处理局部任务，符号控制面的作用是让不同系统使用同一套概念、关系、条件和行动语义。点到为止，不逐项比较技术，不要求证明相对每一种技术组合的增量，也不展开执行工具的责任清单。
- **建议落点**：第 5 节控制面职责、第 7 节四层架构。
- **验收标准**：用一段普通读者能看懂的话回答“为什么已有工具之外还需要符号控制面”即可；相关内容不能改变文章议程或抢占主线篇幅。

## ISSUE I4-02：扩展大语言模型的系统角色（原扩展方案不采纳）

- **优先级**：P1
- **类型**：工程边界
- **评审状态**：原扩展方案不采纳；限定范围通过，未执行；实施须另行取得明确授权。
- **原建议**：把大语言模型从候选生成扩展到证据导航、规划、工具编排、测试生成、验证器选择和异常解释等多种角色。
- **不采纳理由**：第四篇的重点不是为大语言模型扩大活动空间，而是尽可能限制模型，并建立符号对模型的支配关系。模型并非只能生成候选内容，但无论承担什么任务，都不能取得与符号系统并列、更不能居于其上的地位。
- **修改动作**：可以简单提到测试生成等有限用途，用来说明模型能够在受约束的范围内提供帮助；无需罗列角色，也不把规划和工具编排扩展成新的自主权。模型的输入、输出和行动范围均由符号结构规定，模型产生的内容必须接受符号检查。模型必须在符号之下。
- **建议落点**：第 3 节适配方法、第 7 节语言界面和控制面。
- **验收标准**：正文承认模型可以承担候选生成之外的少量辅助任务，但不扩张其系统地位；读者能够明确看出符号负责规定边界、检查结果和约束行动，模型始终处于从属位置。

## ISSUE I4-03：增加同任务比较与经济性指标（不采纳）

- **优先级**：P1
- **类型**：证据验证
- **评审状态**：不采纳，关闭，未执行。
- **原建议**：用同一任务比较单模型、检索增强、规则系统、本体控制面和混合架构，并给出精确率、误授权率、延迟、维护工时和迁移成本等指标。
- **不采纳理由**：目前没有足够、可靠且可公开的证据支持这种横向比较。勉强制作指标和基线表既不能证明文章的主张，也会把讨论带向无法负责的实证结论。
- **关闭边界**：不补实验，不制作比较表，不暗示已有不可公开的比较结果。后续执行第四篇时，凡是依赖此类数据的性能、可靠性或经济性优势表述，只能弱化为有边界的判断；无法可靠表述的，直接删除。

## ISSUE I4-04：增加“制度化错误”与不确定性处理

- **优先级**：P1
- **类型**：逻辑边界
- **评审状态**：限定范围通过，未执行；实施须另行取得明确授权。
- **问题**：符号系统不会因为采用了形式化表达就自动正确。错误一旦进入统一本体，确实可能被稳定地重复执行，成为“制度化错误”。但也正因为认识被明确写出，公司才有机会发现错误、追溯错误并统一纠正错误。
- **修改动作**：在文章结尾用一小段点明：模型的错误往往是临时输出中的错误，而本体中的错误可能进入公司的稳定认识；优秀的本体论企业不是假定自己永远正确，而是能够让错误变得可见、可讨论、可纠正，并让纠正后的认识重新成为全公司的统一依据。可以顺带说明“符合当前规则”不等于“现实中必然正确”，不展开复杂的不确定性状态和申诉流程。
- **建议落点**：结论收束处，作为全文点睛，不另设庞大治理章节。
- **验收标准**：结尾同时说清制度化错误的危险和本体论企业纠正统一认识的能力；这一段应提升文章价值，而不是把主旨转成错误处理手册。
